# Модуль парсинга

Собирает материалы из источников, настроенных в БД: с некоторой периодичностью
опрашивает каждый источник, забирает новые публикации и отсекает повторы по
URL и хешу текста. Живёт в [`backend/app/parsing`](../backend/app/parsing).

## Как это работает

```
Source (БД, правится через интерфейс)
   -> PollingScheduler   расписание: у каждого источника свой интервал
   -> Fetcher            rss | website/regulator | telegram
   -> FetchedDocument    что нашли в источнике
   -> normalize_parser_payload   единственная точка нормализации (RawItem)
   -> store_raw_items    отсечение повторов -> raw_items
```

Слой хранения общий с ingest внешнего парсера, поэтому анализ, API и интерфейс
работают с материалами парсера как с любыми другими.

## Источники

Три категории из ТЗ покрыты типами источников:

| Тип источника | Fetcher | Что опрашивается |
| --- | --- | --- |
| `rss` | `RssFetcher` | RSS 2.0 и Atom: СМИ, агрегаторы, ленты ведомств |
| `regulator`, `website` | `WebsiteFetcher` | сайт без ленты: индексная страница -> страницы материалов |
| `telegram` | `TelegramFetcher` | публичный канал через веб-превью `t.me/s/<channel>` |
| `manual`, `unknown` | — | не опрашивается, материалы добавляются руками |

Стартовый список — [`backend/config/default_sources.json`](../backend/config/default_sources.json):
СМИ (РИА, Интерфакс, РБК, Коммерсантъ), регуляторы (Банк России, Правительство
РФ, Госдума) и Telegram-каналы. Он только добавляет
недостающие источники и никогда не перезаписывает правки пользователя.

## Настройки источника

Расписание и поведение fetcher-а редактируются вместе с самим источником:
`poll_interval_minutes` и JSON-поле `config`.

| Ключ `config` | Тип | Значение |
| --- | --- | --- |
| `fetcher` | строка | переопределяет fetcher: лента регулятора остаётся `regulator`, но читается как `rss` |
| `max_items` | число | сколько материалов забирать за один опрос |
| `fetch_full_text` | флаг | догружать статью, если лента отдаёт только заголовок |
| `full_text_threshold` | число | ниже скольких символов текст считается неполным, по умолчанию 400 |
| `link_pattern` | regexp | какие ссылки индексной страницы считать материалами |
| `same_host` | флаг | ограничить обход доменом источника, по умолчанию да |
| `min_anchor_chars` | число | минимальная длина текста ссылки, если `link_pattern` не задан |
| `min_text_chars` | число | короче — страница не считается материалом, по умолчанию 200 |
| `min_line_chars` | число | порог отсечения навигации, `0` отключает фильтр |
| `channel` | строка | канал Telegram, если отличается от `url` |

## Отсечение повторов

Три уровня, от дешёвого к точному:

1. **До загрузки.** Ссылки, уже лежащие в БД, не скачиваются повторно — обычный
   опрос сайта стоит один GET, пока нет новых публикаций.
2. **Условный GET.** Сохранённые `ETag` и `Last-Modified` уходят обратно
   источнику; ответ `304` завершает опрос без разбора.
3. **При записи.** `store_raw_items(skip_duplicates=True)` отбрасывает материал,
   если совпал канонический URL (без `utm_*` и хвостового `/`) или хеш текста.
   Хеш и ловит один материал, приехавший из разных каналов.

Ingest внешнего парсера (`POST /api/ingest/parser`) работает по-прежнему:
он сохраняет все присланные записи и складывает совпадающие в один event
cluster, чтобы в карточке были видны все источники.

## Запуск

Планировщик стартует вместе с backend и каждые `PARSER_TICK_SECONDS` секунд
опрашивает источники, у которых истёк их интервал. Список читается из БД на
каждом тике, поэтому правки через интерфейс применяются без перезапуска.

Без API модуль запускается сам по себе:

```powershell
..\.venv\Scripts\python.exe -m app.parsing --seed --list
..\.venv\Scripts\python.exe -m app.parsing --source src-cbr-events
..\.venv\Scripts\python.exe -m app.parsing --all
```

## Интерфейс

Страница «Источники» — рабочее место для управления сбором: добавление,
включение и выключение, редактирование названия, адреса, типа, интервала и
`config` (JSON проверяется перед отправкой), кнопка «Опросить» у каждого
источника и «Опросить все» для всего списка. В строке видны статус последнего
опроса, его время, текст ошибки и число собранных материалов; клик по этому
числу открывает ленту, отфильтрованную по источнику. Лента на вкладке
«Сегодня» обновляется сама раз в минуту, пока открыта и не выбрана карточка.

## API

| Endpoint | Назначение |
| --- | --- |
| `POST /api/sources/{id}/poll` | опросить источник сейчас, вернуть отчёт |
| `POST /api/parser/run` | опросить по расписанию, либо `{"force": true}`, либо `{"source_ids": [...]}` |
| `GET /api/parser/status` | состояние планировщика и отчёты последнего запуска |
| `POST /api/sources/import-defaults` | добавить источники по умолчанию |

Отчёт об опросе: `status` (`ok`, `not_modified`, `skipped`, `error`), сколько
материалов получено, сохранено и отсечено как повтор, предупреждения и ошибка.
Те же поля видны у источника: `last_status`, `last_polled_at`, `last_error`.

## Переменные окружения

```env
PARSER_ENABLED=true              # фоновый планировщик
PARSER_SEED_DEFAULTS=true        # посев источников по умолчанию при старте
PARSER_TICK_SECONDS=60           # как часто проверять расписание
PARSER_DEFAULT_INTERVAL_MINUTES=30
PARSER_TIMEOUT_SECONDS=20
PARSER_MAX_ITEMS_PER_POLL=25
PARSER_CONCURRENCY=4
```

## Допущения и ограничения

- Извлечение текста с произвольного сайта — объяснимый baseline на стандартной
  библиотеке: `<article>`/`<main>` в приоритете, навигация отсекается по длине
  строки. Часть служебных блоков на отдельных сайтах остаётся в тексте;
  настройки `min_line_chars`, `link_pattern` и `min_text_chars` — штатный способ
  это поправить, точные правила разметки под конкретное ведомство пишутся после
  того, как видно реальный результат.
- Telegram читается через публичное веб-превью: приватные каналы и каналы с
  выключенным превью честно возвращают ошибку опроса, Bot API не используется.
- Планировщик живёт в процессе backend и подходит для прототипа; для нескольких
  реплик нужна внешняя очередь, чтобы источник не опрашивали параллельно.
- Работа с БД синхронная: на время записи event loop занят. Для объёмов
  хакатона это незаметно, для промышленной нагрузки нужен отдельный worker.
- `robots.txt` не проверяется, ограничение частоты — только интервал источника
  и `PARSER_CONCURRENCY`.
- Ошибка одного источника не останавливает остальные и не роняет цикл: она
  видна в `last_error` и в отчёте опроса.
